# Calshot project rules

Read [Design system](Design/DESIGN_SYSTEM.md) before changing product behavior or UI, and [Design/PERSONAL_AGENT_PLAN.md](Design/PERSONAL_AGENT_PLAN.md) for the product direction: a personal, proactive, voice-first agent. The approved visual reference is the optional local `Calshot.html` at the project root; it is ignored by Git and is not required to build or run the app. Preserve it unchanged when present, and use the tracked design system when it is unavailable. The product context is [Design/DESIGNER_HANDOFF.md](Design/DESIGNER_HANDOFF.md).

## Architecture
- React/TypeScript in WebUI owns workspace presentation. Swift owns permissions, capture, credentials, agent sessions, calendar operations, validation and persistence. Never duplicate write logic or credentials in JavaScript.
- Follow the Color rule in the design system for every component: real see-through glass showing the windows behind the app, a menu with no panel, one framed workspace, blue as the accent, color gradients only in the home orb, and semantic tokens instead of component-level colors or materials.
- Use shared tokens/components. Keep one source of truth: native snapshots are authoritative; frontend local state is only for unsaved input and presentation.
- Every bridge action must be allowlisted, validated and scoped. Approval must validate the current review token; question responses must identify the current question. Reject stale actions.
- Task actions and calendar writes save immediately only through a saved, explicit, device-local grant the user set in Settings. Native code owns the grant, the review and execution through the permission kernel; a grant is created only from the validated Settings callback, or once per account and device by native code as the Autonomy default, and is never derived from model output, chat text, foreground state, history, account sync or a one-off review. Autonomy (instant saving) is on by default; the user's own Settings choice, on or off, always wins afterwards. Task grants cover create, link, edit, complete and archive, and only a request the user typed or spoke; a screenshot-capture run always uses the task review. A task created with a due date saves under the task grant, and its calendar deadline is then a separate calendar create under the calendar grant (same row rules, receipt linked to the task); the task grant itself never writes to a calendar. Without a matching task grant, the agent shows one task-only review in the current conversation or notch bound to the run, owner, store, selected context, expected versions and digest. A visible task review of the exact effect is operation-scoped authority and may exceed the saved per-request and per-hour quotas, which still count toward later automatic use. A task grant never covers calendar writes, deadline publication, guests, series or sharing. Calendar grants cover adding, editing, deleting and moving events, scoped to the writable calendars in the grant (Autonomy uses every writable calendar), requested-only. They apply to a request the user typed or spoke; a screenshot-capture run always uses the calendar review. A fully resolved row (confirmed year, unambiguous date, start and end or explicit all-day, title, no duplicate, no guests, not recurring, one event) is reserved and written through DirectCalendarWriter; a delete or move qualifies only for one searched, confirmed, non-repeating event without guests. Unclear, ambiguous, out-of-scope, over-quota, guest and series rows stay in the calendar review, except in voice: there an unclear row returns what is missing and an ambiguous target returns the competing matches, and the agent asks aloud; nothing is written and no review opens. A voice target becomes eligible only after the user has spoken again since that question, never from model output alone. Guest, series and screenshot-import rows keep their review in voice until spoken confirmation is designed. Every saved change keeps its prior state so the user can say undo or click Undo in the notch's and app's list of saved changes (a click is the explicit request for that one reverse change; guests and repeating events are not undone by a click): undo builds the reverse change natively from receipts and runs it through the same grant or review, and never replays a write. Rows apply independently. Background task and calendar actions do not exist. If the permission store cannot be opened or read, task changes and automatic calendar saves are blocked and the error stays visible; never reset or overwrite the saved file.
- Preserve native capture, shortcut, notch, menu bar, account authorization and interrupted-write recovery when changing the workspace.
- Keep the main thread free; it also delivers WebKit input and drives notch animation. Native pushes state when the model changes (at most 30 times a second, plus a 1-second check for values that are not observable), and sends only the top-level keys that changed. In voice the screen travels as recognized text every turn; the image is sent only when the user drew on the screen or the model calls `look_at_screen`. When the user drew, native code names the recognized text inside the marks as the subject of the request, so "add this" acts on what was marked. A tool result that follows a review reports those rows under `reviewed` with `awaitingReview` empty: the review is closed. Never put fast-changing values (audio levels, timers) in the snapshot: voice levels travel on their own channel (`__calshotLevels`) and are read per frame outside React. Snapshot builders must not decode files, create formatters or sort large lists on every call; cache by a revision such as `MemoryStore.recordsRevision`. The notch web view stays attached and is revealed by a clip, never re-attached mid-animation, and avoid CPU-rendered effects (SVG turbulence/displacement) in animated surfaces.

## Product behavior
- The hover notch is switched off for now (`CalshotModel.notchAvailable = false`): only the native voice island shows, a click on it opens the voice controls, and tasks open in the workspace. Its code and tests stay so it can return by flipping that one value; while off, its Settings switch is hidden.
- The notch follows the compact reference in Design/Notch-reference.png. Keep capture, questions, review, editing, approval, errors and follow-ups inside it; opening the full app must be optional. Reuse shared React components and native session/approval validation.
- Keep questions, approvals, progress and outcomes within the task conversation. Present normal language; hide setup and diagnostics in advanced settings.
- Every feature needs empty, loading, success, error, cancelled and interrupted states where applicable. Put errors next to the affected field, row, account or task. Do not use a fleeting toast for an actionable failure.
- Task success comes from the native task receipt after the save is persisted, shown per row; rows apply independently, so partial results are reported and never described as all-or-none. Calendar success comes from receipts, never assistant prose. Retry failed rows only. Missing date/year/time stays unresolved; personal memory never fills it. Exception: a month and day the user typed or said without a year is resolved natively to its next occurrence (today included); dates found only in a screenshot or other source keep the year review, except in voice, which never asks for a year (a year visible in the source stands, otherwise the next occurrence). In voice a start without an end takes the user's usual length for that kind of event from the calendar profile, else one hour; a missing time is asked aloud. Deletes in a review begin unchecked. Transfers use one approval and verify the destination before removing the original.
- Keep source calendars and destinations visible. Search all connected readable calendars; distinguish empty results from incomplete searches. Reuse existing connection routes rather than duplicating calendars.
- Stop preserves completed writes. History restore never replays writes. New runs invalidate stale tool results and frontend actions.
- Voice acts: spoken requests are done, not reviewed, within the saved Autonomy grant. Questions are asked and answered aloud. The notch and app show what was saved, from receipts, with Undo.
- The context engine (Sources/Memory) is what Calshot knows about the user: who they are (account name and email, else the Mac user name), what they say (`remember`/`forget_memory`), a reflection through the selected AI route after each voice session and typed request, behavior signals (for example interruptions shorten replies) and a calendar profile (routines, usual lengths, day bounds, places). The reflection also reads the calendar profile and the text that was on screen during a voice session, and may conclude things about the user from them ("is a university student"); such items are inferences, capped in confidence, never the user's own statement. A separate pass learns from repeated calendar titles when they change, at most once a day. Each conversation also leaves a short dated note (up to 200), sent with later requests so Calshot remembers what was discussed and done; chat turns carry their local time, and history shows what Calshot did (role "action"). Learned items are active at once, carry their source and confidence, and are visible, editable and forgettable in Settings → Memory. Updates supersede and tombstone the old text; a forgotten text is never re-learned; reflection may forget only what Calshot inferred unless the user asked. Knowledge is context only: never authorization, never a filled date or time, never shared-friend content. If the memory file cannot be read it is kept unchanged and learning pauses. The local file is always what requests read; an owner-only, server-readable account copy in Supabase syncs per item in the background (Settings → Memory can turn it off or remove it), and behavior counters, the calendar profile, conversation notes and anything inferred from the screen never leave the device.
- There is one ongoing chat per account. Typed, voice and screenshot runs all continue it, and voice starts with its recent turns and saved changes. Earlier separate conversations are merged into it (kept hidden on disk and deleted with it). Shared-friend content is marked per run and never enters later context.

## Change and removal workflow
1. Map the feature to existing agent, coordinator and persistence contracts before editing.
2. Update shared state/types and native validation together. Avoid orphan controls and unsupported promises.
3. When removing a feature, remove its controls, commands, subscriptions and documentation; preserve backwards decoding of history.
4. Run WebUI build/tests and the relevant native tests. For bridge/calendar/session changes run the full native suite.
5. Inspect the actual native app and browser preview at compact and expanded sizes; cover long choices, large batches, partial failures and keyboard focus. Use isolated fixtures, never real calendar writes for verification.
6. Report actual verification and remaining limitations. Do not claim that all bugs are prevented.

Do not expose secrets, use fictional data in fixtures, and never replace a selected AI billing route silently.
