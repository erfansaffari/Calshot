# Tasks and deadlines

Status: first implementation. The owner approved a separate Tasks page, connected-calendar deadlines for dated tasks, and tasks/deadlines before smart planning. Calendar presentation is preserved. The earlier `Task-calendar-concept.html` is an exploratory prototype, not the shipped layout.

## Implemented flow

Tasks has its own sidebar item and page. Users can add a title-only task, edit details, complete/reopen, drag or use visible arrow buttons to reorder, archive and restore. Views include All tasks, Today & overdue, Upcoming, Inbox, Completed and Archived. Manual order is stored independently of date sorting. Reordering never changes deadlines. Native snapshots own persisted data; React keeps unsaved form inputs and presentation state only. Errors remain by the form, affected task, or sync controls.

The task editor is progressive: a title-only add row, with date, time, notes, reminder and calendar choices revealed on demand. The sidebar order stays stable (Assistant, Calendar, Tasks, History, Settings). The Assistant start screen shows a compact read-only summary (counts, up to three next tasks, concise due text, View all / Open Tasks). Its rows only navigate to Tasks; completion, creation and every other task write happen on the Tasks page, because native task writes are accepted only while Tasks is the active page. The summary keeps its loading, empty and error states, and is hidden until a native task snapshot exists.

A task may have a date, optional exact due time, timezone, notes, source evidence and an explicit Mac notification. Date-only tasks never gain an invented 11:59 PM time. Strict native date validation rejects impossible dates and nonexistent daylight-saving times.

Every dated task publishes a linked deadline to a selected writable connected calendar unless the user chooses Tasks only. It is an all-day, one-day entry above the timetable, marked free/transparent through EventKit, Google, Outlook or iCloud. An exact due time remains in its title, notes and task fields. It does not reserve a work session. The user's own Save in the task editor is the confirmation: the editor states what Saving will add, update or remove, and native code then writes that one entry directly through `DirectCalendarWriter` (fresh read of the current entry, duplicate check, pre-write journal, current task version, provider receipt). There is no second review and no conversation or History record. Only the receipt marks the deadline as published. A duplicate stops the write and the row offers Add anyway; other failures stay on the task row with Try again. Task storage success never implies calendar success. Deadlines prepared by the agent still use the batch review inside the conversation. Linked updates first read their original event; an unavailable original never triggers an automatic replacement. Edits to a linked deadline are managed on its source Mac. Other Macs can complete or reorder the task.

Completing or archiving cancels a task’s pending Calshot notification and retains its historical provider deadline. Clearing a previously published date, or choosing Tasks only for a published task, removes that entry when the user saves; the editor says so before saving. Delete (in the editor and on archived rows) removes the task from Tasks after one confirmation. Removing its deadline entry is a separate checkbox that starts unchecked; otherwise the entry stays as an ordinary calendar event. A deadline owned by another Mac is never removed from here, and a linked source event is never changed. Deletion syncs without a schema change: a task that was synced before, is missing on one side and is unchanged on the other is treated as deleted; an edit made elsewhere after the delete keeps the task, and nothing is inferred when the server has no saved state. Older app versions that predate this rule can upload a deleted task again.

In Calendar, a task's own deadline entry (identified by its `Calshot task: <id>` marker and an existing task on this Mac) offers Edit task instead of Edit event/Delete event, so the task and its entry stay in step. An interrupted direct save is confirmed later from its journal, never retried, and the result stays visible on Calendar and Tasks until dismissed.

The agent has `list_tasks` and `create_tasks`. Requested assignments, to-dos and actionable deadlines use task storage; actual meetings, classes, scheduled exams and shifts remain calendar events. Imported tasks and dated deadlines share one explicit native approval; Skip saves neither. Inbox rows can be selected individually. Task-import receipts distinguish persisted task records from calendar receipts. Undated or unresolved-year tasks remain in Inbox with source evidence. Dated items use the same batch calendar review inside the existing conversation/notch. Repeated identical imports return existing task IDs rather than duplicating them. There are no agent task-update or planning tools yet.

## Calendar display of deadlines

Calendar classifies events in `WebUI/src/calendarEvents.ts`; it is display only and never writes. The provider’s all-day flag is authoritative: a provider all-day event covers its first day through the last included day in its own timezone. The end is exclusive, and EventKit’s 23:59:59 final day is handled. Duration alone never makes an event all-day, so an unmarked 12:00 AM–11:59 PM event, an overnight shift or a 24-hour block stays timed.

The only other all-day source is the metadata block Calshot appends to linked task deadlines (`Calshot task: <id>`, `Deadline: <date> [at HH:mm] · <zone>`, `This deadline does not reserve work time.`; HTML-wrapped notes are read too). A timed copy created before deadlines became all-day displays as all-day only when every condition holds: the metadata is complete with a real date and zone, the event starts at exactly 00:00:00 on the deadline date in the metadata’s zone, and it ends inside that same day. Anything moved, extended, crossing midnight, starting even a second later, or lying elsewhere on the deadline day stays timed, so a real appointment on a deadline day is never hidden. The due time is shown in event details only when the metadata date is one of the days the entry covers. Week cells show three all-day entries then a `+N more` link into Day; Day lists all of them, and Month keeps its existing three-entry cells.

Limitation: this reclassification is presentation only. The earlier timed copy stays timed at the provider, in other calendar apps and on other devices, and Calshot cannot convert it automatically because it never edits calendar events without a reviewed approval. Detail view offers an explicit **Make all-day** action for writable, non-shared timed events. It only prefills the Calendar assistant request (naming the provider’s real stored range and keeping title, notes, location and calendar); the user sends it, the agent’s `update_event` proposes `allDay`, and nothing is saved until the user approves the review. Provider all-day, read-only, unavailable and shared events do not offer it. Converting a linked deadline this way is an ordinary calendar edit, not a task edit; a later task update still goes through the linked-deadline review on its source Mac.

## Reminders

Mac reminders are explicit local notifications, independent of calendar time. Choices are None, At deadline, 1 hour before and 1 day before. A date-only task needs a visible chosen reminder time; it remains separate from the task’s due time. Swift owns notification permission, scheduling and cancellation. Versioned notification identifiers and session checks reject stale scheduling work. Completion, archive and sign-out clear pending reminders; new-account loads clear previous-account notifications. Permission denial or scheduling failure appears on Tasks. The UI promises scheduling, not guaranteed delivery; macOS controls delivery and notification settings. The web does not deliver reminders.

## Persistence and sync

`Sources/Tasks/CalshotTasks.swift` stores `tasks-v1.json` atomically with restrictive file permissions inside the existing account-specific history directory. A corrupt file stays untouched and blocks mutation. Matching receipts in this Mac’s history repair a missed task receipt after interruption; recovery never replays writes. A failed account load clears the visible task document rather than exposing the previous account’s tasks.

The private web repository owns migration `20261022163253_personal_tasks_and_deadlines.sql`, `public.task_state`, owner RLS and scoped invoker RPCs backed by private authenticated functions. Read/write calls derive identity from Supabase, require verified accounts and validate bounded task documents. Revisions reject stale cloud writes. Per-task version baselines merge independent edits; conflicts require explicit Keep both. A retained local copy has a new ID and no calendar receipt or enabled reminder. Sync never executes calendar proposals or replays history.

The authenticated website imports the same Tasks presentation read-only, with an explicit Mac handoff for editing and calendar approval. Client credentials and native write logic stay in their existing owners.

## Verification and scope

Native tests cover strict dates/DST, account storage and corrupt-file isolation, stale actions, WebKit numeric/boolean types, approval ownership/version checks, explicit calendar approval, ordering/completion/archive, unresolved-year imports and sync conflicts. React interaction tests cover title-only creation, captured edit tokens and preserved input, reorder payloads, persistent errors, archived tasks and the read-only web view. Database checks use fictional users inside rollback transactions, including hosted RLS and revision-conflict verification. The hosted migration source checksum matches the private migration file.

Inspect compact and expanded native/browser layouts with isolated fixtures (`--tasks-preview` and `?preview=1&scenario=tasks`). No real calendar writes are needed. OS notification delivery and live model extraction remain separate integration checks.

## Deferred

Smart planning, effort estimates, work-hour preferences, linked work sessions, custom alarms, task sharing, web mutations, task details opened from calendar chips and a redesigned all-day band are deferred. Calendar currently uses its existing separate bounded all-day row; this feature adds no task overlay or side panel. Planning must eventually read fresh calendar coverage and propose work sessions for approval, while excluding free deadline entries from busy time.
