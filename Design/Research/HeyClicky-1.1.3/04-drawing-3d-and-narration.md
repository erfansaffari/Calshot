# Drawing, generated 3D, and synchronized narration

## What is generated

HeyClicky ships a custom drawing engine and a custom 3D recipe layer. A model produces a short program describing an explanation. Its parts, geometry, colors, labels and animation are resolved locally. The inspected path builds procedural geometry using a subset of Three.js and displays it through native Metal. This directly answers whether the effect is a generated video or a remote text-to-3D model: the bundled implementation of this feature builds and animates a local scene. No conclusion follows about every other media feature in the product.

## From model tokens to a picture

1. **Model output.** `OneBrainClient.Reply` includes drawing code, a spoken sentence, model identifier and other events. `ScreenDrawingStreamState` records partial program text, lines, pointer/card output, display selection, earlier code, and follow-up state. The packaged engine exposes a compact drawing vocabulary for lines, shapes, labels, cards, charts, timelines, photos, pointers and figures.
2. **Incremental execution.** The engine scans for usable statement boundaries and has a session that consumes new statements without re-running the entire prefix. The native bridge feeds the code accumulated so far and analyzes a complete portion as it becomes available. Earlier marks have IDs and bounding boxes and can be addressed by follow-up edits. The running session supports edits such as moves, recoloring, erasure and additions.
3. **Native 2D rendering.** The bridge runs in JavaScriptCore. It supplies a small in-memory SVG DOM façade for the engine and drains render operations. Those operations describe geometry, units, text, clipping and motion. Swift types include a painter, pen stroke/mark timing, text shaper and clocks. Resource code explicitly describes Core Animation for display and Core Text for measurement. The application also ships 2D helpers that encode familiar visual structures and can delegate pointer/button surfaces to the host. 4. **Native screen anchoring.** The main capture record keeps the display frame, display point dimensions, raster size and cursor-display flag. Native drawing stores a display frame, canvas size and screen-under-drawing state. A stale watcher and native follow-up state account for a changing desktop. The data supports both anchored instructions and more free-standing explanation cards. Runtime invalidation thresholds remain unverified.

## Where the 3D mesh comes from

The bundled engine's `figure()` interface establishes the stage, then accepts named parts and their recipes. Recipes include dimensions, axis, stretch, placement, material and scene relationships. Parts may be repeated or mirrored. A figure can also carry per-frame pose changes, such as rotating gears and changing a piston position.

- **Geometry worker.** The 3D kernel in Swift has a dedicated queue, a JavaScript context, recipe cache, memory counters, failed/queued sets and an idle-release mechanism. The resource comments and code identify a separate JavaScriptCore context for geometry, away from the drawing context. The geometry worker returns position, normal, UV and index arrays, plus framing samples.
- **Built-in shapes.** The packaged recipe methods include boxes, cylinders, cones, tubes, arrows, lathes, spheres, tori, capsules, pipes, springs, gears, extrusions, blobs, polygons and surfaces. A soft-shape implementation uses a sampled field and surface nets for smooth forms. A constant caps vertices at 120,000 per part. That cap is per part. The study did not establish a whole-scene budget.
- **Cache and pacing.** Recipe processing can begin when the statement arrives, before the speech beat reveals it. The recipe cache lets repeated parts reuse geometry. The bundle ships a Three.js 0.186.1 subset as an attributed dependency. Local logic implements the part recipes and interactive presentation.
- **Metal stage.** `ScreenDrawing3DStage` owns the layer, display-link state, scene, camera yaw, placement, part labels and hit interaction. `ScreenDrawing3DRenderers` contains device, command queue and object, text and overlay pipelines. There are illustrated and studio looks. The stage tracks a part ID/name on click, label positions and drag state. The vendor shows a figure can rotate and support a spoken follow-up about a component. Exact hit-testing math and model context after a click remain unverified.

## How the picture advances with speech

The engine groups visible marks around narration lines. The bridge exposes a line event and a line-duration event, and feeds these back into the running timeline. The engine can distribute strokes over the corresponding measured duration. Buttons and linked hotspots can wait until the marks for their beat have been revealed. `RealtimeWalkthroughSync` holds beat fractions, drawing lead, playback fraction and completion waiters. The per-line speech ledger and native caption callbacks give the app hooks for voice progress independently of how quickly the model finishes generating the program.

The resulting flow is **stream code → prepare marks and meshes → start narration beat → reveal its drawing → activate accompanying controls**. Large geometry can be prepared ahead of playback while text and canvas continue. A following beat can advance presentation even if every previous mark did not take its ideal time. The engine exposes pause, resume and immediate finish for different interruption paths. The exact audio buffering strategy and beat lead in a live run are unmeasured. ## Saved explanations

A lesson draft carries model, drawing program, canvas/display dimensions, speech lines, duration, audio, poster and photos. Its recorder tracks line starts and captured narration audio. A player, inline viewer, separate panel and printer-related renderers are present. This shows a lesson replay architecture. The 1.1.5 release separately announced retaining every drawing in chat, so that later behavior should not be assumed for every 1.1.3 drawing.
